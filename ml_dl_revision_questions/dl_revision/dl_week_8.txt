## 2. 🎯 TEACH IT SUMMARY

### The Big Picture — Week 8 DL

Week 8 covers **the engineering side of deep learning**: how to take models from research to production (MLOps) and how to train them at massive scale (distributed training). This is where deep learning meets systems engineering.

**Part 1: MLOps (L1).** Machine learning in production is fundamentally different from research. Research prioritizes model performance on static benchmarks; production must satisfy **multiple stakeholders** (ML team, product, sales, management) with competing objectives — accuracy, latency, cost, interpretability. Production data is messy, constantly shifting, and full of privacy concerns. ML systems are **part code, part data** — you need to version and test both. Failures come in two flavors: **ops failures** (software crashes, network issues) and **ML failures** (distribution shifts, edge cases, degenerate feedback loops). Monitoring and observability are critical: track operational metrics (latency, throughput) and ML-specific metrics (accuracy, predictions, features). Reproducibility is hard — same model + same hyperparameters ≠ same results, due to randomness in data ordering, hardware, library versions, and initialization. Tools like **Weights & Biases (W&B)** help track experiments, version data, and visualize results. For deployment: **quantization** reduces precision (FP32 → INT8) for faster inference, **distillation** trains a small "student" model to mimic a large "teacher," and **TorchScript** optimizes models for production serving.

**Part 2: Distributed Training (L2).** Modern LLMs like Llama3-405B are too large for a single GPU. Distributed training splits the work across many GPUs using **communication collectives** (All-Reduce, Reduce-Scatter, All-Gather, All-To-All). There are **five parallelism strategies**, each splitting a different dimension of the activation tensor (Layer, Batch, Sequence, Channel): **Data Parallelism (DP)** splits the batch; **Context Parallelism (CP)** splits the sequence; **Pipeline Parallelism (PP)** splits the layers; **Tensor Parallelism (TP)** splits the channels; **Expert Parallelism (EP)** splits MoE experts. **FSDP (Fully Sharded Data Parallelism)** shards model weights across GPUs, and **HSDP (Hybrid Sharded Data Parallelism)** combines FSDP within groups with DP across groups. **Activation checkpointing** trades compute for memory: instead of storing all activations, recompute them during the backward pass. The goal is to maximize **MFU (Model FLOPs Utilization)** — the fraction of theoretical peak FLOPs actually used for useful computation. The scaling recipe: use DP up to ~128 GPUs, FSDP for >1B params, HSDP for >256 GPUs, and advanced strategies (CP, PP, TP) for >1K GPUs.

**The Connecting Thread:** Week 8 shows that deep learning is not just about models — it's about systems. The same model that achieves state-of-the-art accuracy in a paper may fail in production due to distribution shift, or may be impossible to train without distributed infrastructure. Understanding these engineering challenges is what separates research from real-world impact.

## 3. ⚠️ COMMON PITFALLS IN PRACTICE

**How to use:** These are practical mistakes that happen in code and experiments. Read each pitfall and the fix before your next project.

| Pitfall | Why It Happens | How to Avoid |
|---------|----------------|--------------|
| **1. Treating ML production like research** | Research optimizes model performance; production has multiple stakeholders | Define a **comprehensive utility function**: accuracy, latency, cost, interpretability, robustness |
| **2. Ignoring data versioning** | Code is versioned with Git; data is not | Use **data versioning tools** (DVC, W&B Artifacts); line-by-line diffs don't work for datasets |
| **3. Confusing ops failures with ML failures** | Both cause system failure but have different causes | **Ops failures**: crashes, network issues. **ML failures**: distribution shift, edge cases, feedback loops |
| **4. Not monitoring predictions** | Predictions are low-dim and easy to monitor | Track **prediction distributions**; changes often indicate input distribution shifts |
| **5. Assuming more data always helps** | Production data is messy, biased, and shifting | **Monitor data quality**; retrain when distribution shifts; use two-sample tests |
| **6. Ignoring degenerate feedback loops** | Model predictions influence future training data | Use **randomization** and **positional features**; be aware of recommender systems and resume screening |
| **7. Not reproducing experiments** | Same model + hyperparameters ≠ same results | Track **random seeds, library versions, hardware, data order**; use W&B |
| **8. Deploying unoptimized models** | Large models are slow and expensive | Use **quantization** (FP32 → INT8), **distillation**, **TorchScript** |
| **9. Using eager mode in production** | Eager mode is flexible but slow | Use **TorchScript** (tracing or scripting) for optimized inference |
| **10. Training large models on one GPU** | Model doesn't fit in memory | Use **FSDP** to shard weights; **activation checkpointing** to reduce memory |
| **11. Ignoring communication overhead** | Distributed training is communication-bound | Use **HSDP** to keep communication local; overlap computation and communication |
| **12. Not measuring MFU** | You don't know if you're using GPUs efficiently | Compute **MFU**: theoretical FLOPs / actual time; >30% is good, >40% is excellent |
| **13. Using the wrong parallelism strategy** | Different strategies suit different model sizes | Follow the **scaling recipe**: DP → FSDP → HSDP → CP/PP/TP |
| **14. Forgetting activation checkpointing** | Activations fill up GPU memory | Use **activation checkpointing**: recompute activations during backward pass |
| **15. Not using communication collectives efficiently** | Naive communication is slow | Use **All-Reduce** (DP), **Reduce-Scatter** (FSDP backward), **All-Gather** (FSDP forward), **All-To-All** (CP) |

### Distributed Training

<details>
<summary><b>GPU Speedup</b> — Try your own first</summary>

**Model Answer:** GPUs have gotten ~1000× faster since 2013 (K40: 5 TFLOP/sec → B200: 5000 TFLOP/sec), making large-scale training feasible.

</details>

---

<details>
<summary><b>Communication Collectives</b> — Try your own first</summary>

**Model Answer:** Primitives for GPUs to exchange data — All-Reduce (sum), Reduce-Scatter (sum + scatter), All-Gather (concat), All-To-All (transpose).

</details>

---

<details>
<summary><b>All-Reduce</b> — Try your own first</summary>

**Model Answer:** Each GPU has a different tensor; each GPU ends up with the sum of all input tensors — used in DDP backward.

</details>

---

<details>
<summary><b>Reduce-Scatter</b> — Try your own first</summary>

**Model Answer:** Each GPU has a different tensor; each GPU ends up with a piece of the sum — used in FSDP backward.

</details>

---

<details>
<summary><b>All-Gather</b> — Try your own first</summary>

**Model Answer:** Each GPU has a piece of a tensor; collect them so each GPU has the whole tensor — used in FSDP forward.

</details>

---

<details>
<summary><b>All-To-All</b> — Try your own first</summary>

**Model Answer:** Break each input tensor into chunks and "transpose" them across GPUs — used to reshard a tensor along a different axis (Ulysses CP).

</details>

---

<details>
<summary><b>Data Parallelism (DP)</b> — Try your own first</summary>

**Model Answer:** Split the batch dimension across GPUs; each GPU has its own copy of the model, computes gradients on its batch, then averages gradients via All-Reduce.

</details>

---

<details>
<summary><b>Fully Sharded Data Parallelism (FSDP)</b> — Try your own first</summary>

**Model Answer:** Split model weights across GPUs; each weight is owned by one GPU (with its grads and optimizer states); broadcast weights before forward/backward, reduce gradients after.

</details>

---

<details>
<summary><b>Hybrid Sharded Data Parallelism (HSDP)</b> — Try your own first</summary>

**Model Answer:** Split N = M*K GPUs into M groups of K; each group does FSDP (splits weights across K GPUs), and DP is done across the M groups.

</details>

---

<details>
<summary><b>Activation Checkpointing</b> — Try your own first</summary>

**Model Answer:** Trade compute for memory — instead of storing all activations, save checkpoints every C layers and recompute activations during the backward pass.

</details>

---

<details>
<summary><b>Context Parallelism (CP)</b> — Try your own first</summary>

**Model Answer:** Split the sequence dimension across GPUs — used for long-sequence finetuning (e.g., Llama3-405B: S=131,072, 16-way CP).

</details>

---

<details>
<summary><b>Pipeline Parallelism (PP)</b> — Try your own first</summary>

**Model Answer:** Split the layers across GPUs; copy activations between layers at GPU boundaries; use microbatches to reduce idle time (bubbles).

</details>

---

<details>
<summary><b>Tensor Parallelism (TP)</b> — Try your own first</summary>

**Model Answer:** Split the weights of each linear layer across GPUs; use block matrix multiply; with 2 consecutive TP layers, shard first over row and second over column to avoid communication.

</details>

---

<details>
<summary><b>Expert Parallelism (EP)</b> — Try your own first</summary>

**Model Answer:** For MoE models, split experts across GPUs — each GPU processes a subset of experts.

</details>

---

<details>
<summary><b>Model FLOPs Utilization (MFU)</b> — Try your own first</summary>

**Model Answer:** The fraction of the GPU's theoretical peak FLOPs used for "useful" model computation — >30% is good, >40% is excellent.

</details>

---

<details>
<summary><b>Scaling Recipe</b> — Try your own first</summary>

**Model Answer:** 1) DP up to ~128 GPUs (models ~1B), 2) FSDP for >1B params, 3) Activation checkpointing for larger batches, 4) HSDP for >256 GPUs, 5) CP/PP/TP for >1K GPUs or >50B params.

</details>

## 5. QUICK REFERENCE CHEAT SHEET — WEEK 8 DL

### Key Formulas

<details>
<summary><b>Data Parallelism Gradient</b> — Try to recall first</summary>

| Aspect | Detail |
|--------|--------|
| **Loss** | `L = (1/MN) Σ_i Σ_j ℓ(x_{i,j}, W)` |
| **Gradient** | `∂L/∂W = (1/M) Σ_i (1/N) Σ_j ∂ℓ/∂W` |
| **Key insight** | Gradients are linear — each GPU computes its own gradient, then average via All-Reduce |

</details>

---

<details>
<summary><b>FSDP Memory</b> — Try to recall first</summary>

| Aspect | Detail |
|--------|--------|
| **Problem** | Each weight needs 4 numbers (weight, grad, Adam β1, β2), 2 bytes each |
| **1B params** | 8GB |
| **10B params** | 80GB (fills up H100) |
| **100B params** | 800GB; split over 80 GPUs = 10GB per GPU |

</details>

---

<details>
<summary><b>Activation Checkpointing</b> — Try to recall first</summary>

| Strategy | Compute | Memory |
|----------|---------|--------|
| **Forward+backward** | O(N) | O(N) |
| **Full recomputation** | O(N²) | O(1) |
| **C checkpoints** | O(N²/C) | O(C) |
| **√N checkpoints** | O(N^1.5) | O(√N) |

</details>

---

<details>
<summary><b>MFU Calculation</b> — Try to recall first</summary>

| Step | Detail |
|------|--------|
| 1 | `FLOP_theoretical = forward + backward` (backward = 2× forward) |
| 2 | `FLOP/sec_theoretical = 989.4 TFLOP/sec (H100)` |
| 3 | `t_theoretical = FLOP_theoretical / FLOP/sec_theoretical` |
| 4 | `t_actual = measured time for full iteration` |
| 5 | `MFU = t_theoretical / t_actual` |

</details>

### Parallelism Strategies

<details>
<summary><b>Parallelism Comparison</b> — Try to recall first</summary>

| Strategy | Split Dimension | Used For | Communication |
|----------|-----------------|----------|---------------|
| **DP** | Batch | Models <1B | All-Reduce (gradients) |
| **FSDP** | Weights | Models >1B | All-Gather (forward), Reduce-Scatter (backward) |
| **HSDP** | Weights + Batch | Models >256 GPUs | Local + global |
| **CP** | Sequence | Long sequences | All-To-All |
| **PP** | Layers | Deep models | Point-to-point |
| **TP** | Channels | Wide layers | All-Reduce |

</details>

<details>
<summary><b>Communication Collectives</b> — Try to recall first</summary>

| Collective | What it does | Used in |
|------------|--------------|---------|
| **All-Reduce** | Sum all tensors; all GPUs get result | DP backward |
| **Reduce-Scatter** | Sum then scatter pieces | FSDP backward |
| **All-Gather** | Collect pieces into full tensor | FSDP forward |
| **All-To-All** | Transpose chunks across GPUs | Ulysses CP |

</details>

### 🔗 KEY CONNECTION EXPLANATIONS

<details>
<summary><b>Connection 1: How does MLOps connect to distributed training?</b></summary>

```
MLOps (L1)                              Distributed Training (L2)
─────────────────────────────────────────────────────────────────────
Experiment Tracking (W&B)          →    Track distributed training runs
    ↓                                        ↓
Reproducibility                    →    Same parallelism strategy + same config
    ↓                                        ↓
Model Serving (TorchServe)         →    Serve large models trained on many GPUs
    ↓                                        ↓
Quantization / Distillation        →    Compress large models for deployment
    ↓                                        ↓
Monitoring                         →    Monitor distributed training metrics (MFU, loss)

The connection: MLOps is about managing the lifecycle; distributed training is about scaling the training phase. Both are essential for production ML.
```

</details>

<details>
<summary><b>Connection 2: How do communication collectives connect to parallelism strategies?</b></summary>

```
Communication Collectives                Parallelism Strategies
─────────────────────────────────────────────────────────────────────
All-Reduce                          →    Data Parallelism (DP) backward
    ↓                                        ↓
Reduce-Scatter                      →    FSDP backward
    ↓                                        ↓
All-Gather                          →    FSDP forward
    ↓                                        ↓
All-To-All                          →    Context Parallelism (CP)
    ↓                                        ↓
Point-to-Point                      →    Pipeline Parallelism (PP)

Each parallelism strategy uses specific communication collectives optimized for its pattern.
```

</details>

<details>
<summary><b>Connection 3: How does FSDP relate to DP?</b></summary>

```
Data Parallelism (DP)                   FSDP
─────────────────────────────────────────────────────────────────────
Each GPU has full model copy        →    Weights sharded across GPUs
    ↓                                        ↓
Model size limited by GPU memory    →    Can train models larger than one GPU
    ↓                                        ↓
All-Reduce gradients                →    All-Gather weights, Reduce-Scatter grads
    ↓                                        ↓
Simple, efficient for small models  →    More complex, but scales to huge models

FSDP is DP with sharded weights — it solves the memory problem of DP.
```

</details>

<details>
<summary><b>Connection 4: How does activation checkpointing connect to FSDP?</b></summary>

```
FSDP                                    Activation Checkpointing
─────────────────────────────────────────────────────────────────────
Solves: model weights too big           Solves: activations too big
    ↓                                        ↓
Shards weights across GPUs              Recomputes activations during backward
    ↓                                        ↓
Frees up memory for weights             Frees up memory for activations
    ↓                                        ↓
Together: Can train massive models      Together: FSDP + AC = scale to 100B+ params

The two techniques are complementary — FSDP handles weights, AC handles activations.
```

</details>

## 7. COMMON MISCONCEPTIONS — WEEK 8 DL

**How to use:** Read each misconception first. Try to identify what's wrong. Then click to reveal the reality.

---

### Misconception 1: "ML production is just ML research with more data."

<details>
<summary><b>Click for Reality Check</b></summary>

| Misconception | Reality |
|---------------|---------|
| Production ML is research + more data. | **Production ML is fundamentally different:** |
| | • **Multiple stakeholders** — ML team wants accuracy, product wants latency, sales wants revenue, management wants profit |
| | • **Computational priority** — Research: fast training; Production: fast inference |
| | • **Data** — Research: static, clean; Production: constantly shifting, messy, biased |
| | • **Fairness & Interpretability** — "Good to have" in research; "Important" in production |
| | • **Failures** — Ops failures (crashes) and ML failures (distribution shifts) |

**Key insight:** Production ML is 10% machine learning and 90% engineering.

</details>

---

### Misconception 2: "If training loss is low, the model is good."

<details>
<summary><b>Click for Reality Check</b></summary>

| Misconception | Reality |
|---------------|---------|
| Low training loss = good model. | **Overfitting alert!** A model can memorize training data (0 loss) but fail on new data. |
| | **What actually matters:** Performance on **validation/test sets** (generalization) and **production metrics**. |
| | **In production:** A model may have high accuracy on the test set but fail due to **distribution shift** — production data differs from training data. |

**Key insight:** Always monitor production performance, not just training loss.

</details>

---

### Misconception 3: "Data distribution shifts are rare."

<details>
<summary><b>Click for Reality Check</b></summary>

| Misconception | Reality |
|---------------|---------|
| Distribution shifts are edge cases. | **Distribution shifts are the norm in production:** |
| | • **Covariate shift** — input distribution changes (new users, new devices) |
| | • **Label shift** — output distribution changes (seasonal demand) |
| | • **Concept drift** — relationship between input and output changes (COVID housing prices) |
| | • **Feature change** — features added/removed/updated |
| | • **Label schema change** — new classes added |

**Key insight:** Production data is constantly shifting — you must monitor and retrain.

</details>

---

### Misconception 4: "Monitoring is enough — you don't need observability."

<details>
<summary><b>Click for Reality Check</b></summary>

| Misconception | Reality |
|---------------|---------|
| Monitoring and observability are the same. | **They are different:** |
| | • **Monitoring** — tracking metrics to determine *when* something goes wrong |
| | • **Observability** — setting up the system to give visibility into *why* something went wrong |
| | • Observability is part of monitoring |
| | • **Instrumentation** — adding timers, counting NaNs, logging unusual events |

**Key insight:** You need both — monitoring tells you something is wrong; observability tells you why.

</details>

---

### Misconception 5: "More data always improves production models."

<details>
<summary><b>Click for Reality Check</b></summary>

| Misconception | Reality |
|---------------|---------|
| More data = better model. | **Not necessarily in production:** |
| | • **Quality matters** — messy, biased data hurts |
| | • **Distribution shift** — more data from the wrong distribution makes it worse |
| | • **Label noise** — more wrong labels = worse model |
| | • **Diminishing returns** — at some point, more data barely helps |

**Key insight:** In production, data quality and relevance matter more than quantity.

</details>

---

### Misconception 6: "FSDP and DP are the same thing."

<details>
<summary><b>Click for Reality Check</b></summary>

| Misconception | Reality |
|---------------|---------|
| FSDP is just DP with a different name. | **FSDP extends DP by sharding weights:** |
| | • **DP** — each GPU has a full copy of the model; limited by GPU memory |
| | • **FSDP** — weights are sharded across GPUs; can train models larger than one GPU |
| | • **DP** — All-Reduce gradients |
| | • **FSDP** — All-Gather weights (forward), Reduce-Scatter gradients (backward) |
| | • **FSDP** — more complex, but scales to huge models |

**Key insight:** FSDP solves DP's memory problem by sharding weights.

</details>

---

### Misconception 7: "Activation checkpointing is free."

<details>
<summary><b>Click for Reality Check</b></summary>

| Misconception | Reality |
|---------------|---------|
| Activation checkpointing reduces memory with no cost. | **Activation checkpointing trades compute for memory:** |
| | • **Forward+backward** — O(N) compute, O(N) memory |
| | • **Full recomputation** — O(N²) compute, O(1) memory |
| | • **C checkpoints** — O(N²/C) compute, O(C) memory |
| | • **√N checkpoints** — O(N^1.5) compute, O(√N) memory |
| | • **The cost:** More compute (recomputation) in exchange for less memory |

**Key insight:** Activation checkpointing is a trade-off — you pay in compute to save memory.

</details>

---

### Misconception 8: "Pipeline parallelism is efficient."

<details>
<summary><b>Click for Reality Check</b></summary>

| Misconception | Reality |
|---------------|---------|
| Pipeline parallelism keeps all GPUs busy. | **Pipeline parallelism has bubbles (idle time):** |
| | • **Problem:** Sequential dependencies — GPUs are mostly sitting idle |
| | • **Max MFU with N-way PP is 1/N** |
| | • **Solution:** Run multiple **microbatches** at the same time, pipeline them through the GPUs |
| | • **Trade-off:** Microbatches reduce bubbles but add complexity |

**Key insight:** PP requires microbatches to be efficient; without them, most GPUs are idle.

</details>

---

### Misconception 9: "Tensor parallelism is always beneficial."

<details>
<summary><b>Click for Reality Check</b></summary>

| Misconception | Reality |
|---------------|---------|
| Tensor parallelism speeds up all models. | **TP has communication overhead:** |
| | • **Problem:** Need to gather parts of Y after forward, can't overlap with communication |
| | • **Trick:** With 2 consecutive TP layers, shard first over row and second over column to avoid communication |
| | • **TP is best for wide layers** (large channel dimension) |
| | • **TP is less useful for narrow layers** |

**Key insight:** TP is beneficial for wide layers but has communication overhead — use strategically.

</details>

---

### Misconception 10: "MFU >50% is easy to achieve."

<details>
<summary><b>Click for Reality Check</b></summary>

| Misconception | Reality |
|---------------|---------|
| You can easily achieve 50%+ MFU. | **MFU >30% is good, >40% is excellent:** |
| | • **GPT-3** — 21.3% MFU |
| | • **Gopher** — 32.5% MFU |
| | • **Megatron-Turing NLG** — 30.2% MFU |
| | • **PaLM** — 46.2% MFU |
| | • **Llama3** — 38-43% MFU |
| | **Why it's hard:** Communication overhead, memory bandwidth, kernel launch overhead, non-matmul operations |

**Key insight:** MFU >40% is world-class; most models achieve 20-30%.

</details>

---

### Misconception 11: "Quantization always reduces accuracy significantly."

<details>
<summary><b>Click for Reality Check</b></summary>

| Misconception | Reality |
|---------------|---------|
| Quantization (FP32 → INT8) destroys accuracy. | **Modern quantization preserves accuracy:** |
| | • **BERT** — 0.902 → 0.895 (dynamic) |
| | • **ResNet-50** — 76.9 → 75.9 (static) |
| | • **MobileNet-v2** — 71.9 → 71.6 (quantization-aware training) |
| | • **Quantization-aware training** — quantization error is part of training error; leads to greatest accuracy |

**Key insight:** Quantization can achieve 2-5× speedup with minimal accuracy loss.

</details>

---

### Misconception 12: "TorchScript is always better than eager mode."

<details>
<summary><b>Click for Reality Check</b></summary>

| Misconception | Reality |
|---------------|---------|
| TorchScript is always faster and better. | **TorchScript vs Eager:** |
| | • **Eager** — good for training/prototyping/debugging; flexible; slow for production |
| | • **TorchScript** — optimized for production; faster; but doesn't support everything |
| | • **Tracing** — doesn't support control flow; requires sample input |
| | • **Scripting** — supports control flow; only requires model |
| | • **TorchScript** — 21-42% faster inference |

**Key insight:** Use eager for development, TorchScript for production.

</details>
